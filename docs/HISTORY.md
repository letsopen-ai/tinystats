# Recorded history

Since 0.33.3, scalar chart time positions are prepared together with immutable dates/domain for reuse by drawing, inspection and accessibility. Core-matrix cadence/gap derivation stays separate. Recorded values, selected statistics, resize, checkpoint format and sampling cadence are unchanged. The component measurements and limits establish less repeated work with bounded retained state, not whole-app memory savings.

Open **History…** from Overview, CPU, GPU, Memory, Network, Disks or Power (battery history). Choose a metric, Peak / Sample average / Minimum, and 10 minutes; 1, 3, 6 or 12 hours; or 1, 3, 7, 14 or 28 days. Since0.29.0, saving defaults On for new/missing preferences. An explicit saved Off remains Off; a malformed explicit value fails closed. **Keep history between launches** is available in General and History, with a shared asynchronous storage action and busy state. With saving Off, only current-session readings are collected and no automatic store access occurs; with it On, retained numeric readings resume on the next launch. Selecting a longer range never creates older data. The chart has a fixed domain for the selected range, dated axis endpoints and a shaded area where there are no recorded observations. It separately labels its actual observed span and ending sample. Paused sampling leaves the last collected projection available.

Six fixed retention rings use numeric buckets of 2, 12, 72, 288, 2016 or 8064 seconds. The intermediate 3h, 12h, 3d and 14d ranges reuse a containing tier rather than allocating more rings. Each view discloses its actual bucket resolution. Up to 300 buckets are displayed/exported; at most 1806 buckets, including unfinished buckets, are retained across all ranges. On every accepted observation, each retained tier releases wholly expired completed/active buckets. A large forward wall-clock jump can therefore expire history permanently before the clock is corrected; system uptime excludes sleep, so this implementation cannot distinguish that jump from a long sleep. The cutoff is anchored to that newest observation; Off or paused history is not automatically deleted by calendar age. The oldest boundary bucket can include observations just before the requested cutoff; CSV gives each bucket's actual first and last sample. No empty buckets or zero readings are synthesized for sleep, Pause or unavailable metrics. A backward wall correction of up to five minutes with advancing uptime holds new samples until wall time catches up, preserving the archive and marking the next accepted bucket partial. A larger backward jump or non-increasing uptime increments the disclosed reset count. In-memory-only mode starts a new timeline; persistent mode keeps older nonfuture buckets and marks a gap. A backward first sample after restoration receives the same protection. Forward gaps are marked; a peak from a partial bucket does not mean continuous coverage.

History CPU percentages use machine processor-state ratios and are unaffected by the [process/self CPU-unit erratum](PERFORMANCE.md#cpu-measurement-erratum-0290).

Peak remains the default. Sample average weights valid recorded observations, not elapsed time; Minimum uses the lowest valid observation. Headline values combine the chosen range with the same rules. Dense display columns use peaks, count-weighted means or minima as selected; rate scales follow the selected values and percentage scales stay fixed at 0–100%. Coverage shows statistic observations / valid readings, separately for each series. It is not a fraction of elapsed time or total observations. Older v1 history has no recorded average/minimum; mixed old/new buckets expose only actually collected statistics and remain marked partial. These are not transfer totals or per-process samples. CPU graphs show the selected total statistic; CSV User/System always come from one actual peak-total CPU observation in each bucket. Upload/download and disk read/write retain independent peaks. Gray markers identify partial/missing readings; orange bands mark observed time gaps and thin orange markers identify gap-containing buckets. These can coexist. Known zero is distinct from missing. The sampler's existing slower sensor/battery readings may appear in several observations; validity counts count observations, not independent hardware reads. Recent 300-point retention and cadence remain in place; startup-capacity history now selects `/` explicitly rather than assuming the first enumerated volume.

CPU History also shows ordered logical-core activity as a heatmap grouped by E/P/unknown kind, with color and shape markers, with the selected statistic and a numeric range value for each core. The resizable window scrolls to every supported logical counter (up to256). Core numbers remain available to accessibility and CSV, without E1/P3 labels on the graph. This is Mach logical-counter order, not inferred physical-core identity. Values from incompatible layouts show gray missing cells in the displayed latest recorded layout. A bucket spanning a count/kind change withholds its per-core values, retains its latest layout and identifies that change in CSV. Missing readings are never zero; legacy checkpoints contain no invented core history. Pixel columns combine peaks, minima or valid-count-weighted means, with partial/gap indicators. Per-core aggregates use compact Float32 percentages and integer counts; they have single-precision rounding, not exact Double statistics.

**Export CSV…** saves a frozen snapshot of the selected range, containing all twelve numeric system metrics, UTC first/last sample bounds, resolution, observation count, gap flags and per-metric valid-observation counts. Empty numeric cells mean unavailable. The first29 columns retain their prior ordering and semantics, including CPU components from the bucket's peak-total CPU observation and validity counts over all observations. Appended columns contain each metric's minimum, sample average and aggregate-valid count, regardless of the selected chart statistic. Component averages/minima are independent and their column names do not say at-peak. Values use percentages, bytes per second or Celsius as named in each column. When core data/layout changes exist, bounded extra columns identify layout-change buckets and each ordered logical counter’s E/P/unknown kind, peak, minimum, sample average and integer valid count. All retained layouts are exported; quarantined mixed-layout values stay blank. The CSV contains no process names, addresses, coordinates, selected-sensor keys or account events. Export uses the native save panel and appends persistent error/success feedback below coverage, clearing it on the next export or range change.

Retention uses the existing serial collector/shared timer and makes no network requests. Optional persistence writes on that same serial worker, with no additional recurring timer. The window's requested projection is coalesced with main-actor deliveries and stops on close or minimization. History does not request process scans or change collection cadence. Charts support numerical inspection on pointer movement, click or drag, with actual sample times and unavailable values. CPU total and logical-core History share a snapped time column. Native click inspection and targeted CUA scrolling at an unchanged input position are verified in History; 0.32.4 evidence distinguishes this from independent no-click OS mouse-move/physical hover and actual menu-bar-icon click delivery, which remain unverified. Historical per-device/GPU-core views and representative long-run/physical sleep/hardware validation remain open. 0.31.0 native/resource evidence and compatibility status distinguish local results from unverified native14/15/Intel execution.

Bjango's [published version history](https://register.bjango.com/mac/istatmenus/versionhistory/) establishes the commercial product's longer selectable history ranges. This is an independent bounded implementation; no proprietary history schema or implementation is copied.

## Recent sensor browsing

The Sensors page has a separate recent graph for whichever sensor you select. It records up to 120 hardware observations while the current detail view is alive, across at most 132 sensor identities. Closing the view releases this buffer; it is not saved across launches. The existing persisted Sensors history continues to represent the selected **menu bar sensor**, and browsing does not change that selection. Search filters only the list. See [sensor browsing](COMPONENTS.md#browse-individual-sensors) for units, gaps and bounds.

## Local checkpoints

Since 0.31.3, the native store restores through a buffer capped at 64 KiB, sharing the existing v1/v2/v3 validation and retention rules without holding the entire encoded file beside the decoded archive. CRC/trailer/EOF must validate before publishing history; corrupt/unsupported files still block saving until confirmed Clear. No format, default/explicit preference or cadence change. Restore peak measurements and limits do not establish lower steady-state/UI memory.

**Keep history between launches**, in **Settings → General** and History, retains up to 28 days of numeric history. It defaults On for new/missing preferences; existing explicit Off choices are preserved. General’s **History & storage…** opens the History window for detailed state, export and Clear. There are no process names, IP addresses, coordinates or account events. Timestamps and gap flags can reveal periods of activity. The private `Application Support/TinyStatsHistory` directory uses mode0700 and its checkpoint/lock use0600. TinyStats requests Time Machine exclusion when enabling and reports verification in storage help; other backups may still retain copies.

Dirty history checkpoints every five monotonic minutes, plus explicit enable and best-effort sleep/normal Quit. Quit has a two-second deadline; disk stalls or abnormal termination may lose readings since the last completed checkpoint. Atomic replacement preserves the earlier file on a failed replacement but does not guarantee power-loss durability. Scalar-only v2 checkpoints contain at most758596bytes; v1 peak-only checkpoints (at most325156bytes) remain readable with unknown aggregate coverage. CPU core data uses v3 at the historical filename `history-v1.bin`, with at most8621920bytes for256 logical counters in all1806 buckets. A saturated10-core file is1069228bytes, including scalar data; actual files allocate only retained buckets and layouts. One atomic temporary copy can coexist during saving, so the two bounded data files can total17243840bytes, excluding filesystem overhead. The cadence stays five minutes. At288 periodic full-file writes/day, theoretical saturated10-core logical bytes are307937664/day and the256-core ceiling is2483112960/day, before enable/sleep/Quit and filesystem amplification. These are bounds, not measured daily writes or a memory optimization. **Before downgrading below0.31 with per-core history (or below0.28 with v2 history), turn saving off; export first if you need a readable copy. Older apps cannot read the newer format and block saving until explicit Clear; turning saving off retains the checkpoint and avoids automatic store access. Clear removes the saved history.** Unknown/corrupt formats block saving until an explicit confirmed Clear. Unsafe support locks require folder repair while the app is closed; Clear never unlinks a possibly busy lock.

**Off pauses saving and keeps the existing checkpoint.** Current readings remain in memory until quit. Re-enabling imports strictly earlier disjoint saved observations, marks the join, and keeps memory authoritative over overlapping aggregates to avoid double counting. Disjoint bounds within one tier slot can combine peaks/counts, minima and count-weighted means; CPU parts remain paired to the chosen total peak. The reset counter uses the maximum known cumulative count rather than adding possibly overlapping counters.

**Clear history…** asks for confirmation before removing all retained History readings and the checkpoint on this Mac. If file removal fails, current in-memory History is cleared but the saved file remains and saving is blocked. Readings collected afterward are not checkpointed until a successful Clear retry; repairing the folder and relaunching can reload the retained file. Cancel leaves both intact. Recent live menu-bar charts remain available; existing backups are unaffected. Clearing is available while saving is off and is the only explicit off-mode store access. Explicit-Off startup, ticks, sleep and Quit perform no automatic store access. Isolated preferences require an explicit test directory, exclude the default profile paths by physical identity and never fall back to its history.

## 0.24.1 close ownership

Closing History clears its native window content before the app discards the controller. A retained-window fixture and actual closed-window heap attribution verify chart/control release. Opening History creates a new controller; this change does not affect retained numeric session buckets. Physical repeated-cycle window growth remains unverified, and no meaningful RSS/footprint reduction is claimed. See ownership investigation.

## History resize refinement · 0.35.4

Enlarging History now gives the aggregate chart the extra height while keeping each logical-core row readable. Single-series charts fill the viewport, Export and the range selector stay at the right edge, and status/storage labels follow the window width. Resizing reuses the existing sample arrays instead of rebuilding the projection. Numerical inspection uses “1 bucket” or plural “buckets” as appropriate. Local regression/native evidence and review distinguish click inspection from unverified independent physical hover. These layout and allocation-path changes establish no whole-app memory saving.
