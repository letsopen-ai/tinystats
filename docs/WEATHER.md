# Weather

**Weather is off by default for new installs**; enabling it is an explicit opt-in. Its menu readout is also unselected by default. No forecast or location requests happen until Weather is enabled. Existing saved Weather choices, including an explicit off state, are preserved. Open the main **Weather** tab (⌘0), use **Enable weather**, then choose **Allow current location…** to request TinyStats' own macOS location permission. Weather's permission cannot be inherited. Merely opening the window or enabling the checkbox never prompts for permission.

Current location uses the same macOS Location Services facility as Weather, through a one-shot coarse fix rather than continuous tracking. TinyStats does not read Weather's current-location coordinates. A current fix is cleared before startup, pause/sleep, source changes and opt-out/re-enable; a stored coordinate cannot start forecasts before a fresh authorized fix. Permission denial and unavailable locations offer a saved city or manual coordinates instead. Forecast time zone follows this Mac for current location.

The main Weather tab's city chooser and **Locations & privacy… → Location source** also show Weather's cached saved cities. Reading that bounded local cache requires no forecast request, private Weather framework or credential. Some macOS versions populate it only after Weather opens; missing, unreadable or changed formats fail closed with a message. Open Weather once, then reopen the page to refresh it. The importer accepts at most 256 KiB and the first 64 entries, validates coordinates/time zones/names and deduplicates coordinates; truncation is disclosed. It never treats a home/search/last-viewed location as current. See research and limits.

For **Manual coordinates**, open **Locations & privacy…**, choose Manual coordinates, enter decimal latitude/longitude and an IANA time zone, optionally name the location, and choose **Apply location**. Applying changes the location only and preserves Weather's current enabled state. Use **Enable weather** on the main tab to start or stop forecasts. Invalid drafts do not apply; closing discards them. Canonical city/enablement changes synchronize the editor while preserving an edited draft. Selecting a saved city makes it the primary forecast/readout location while keeping the enable switch unchanged; TinyStats does not request forecasts for every saved city in the background.

Open **Weather** in details (⌘0), or enable its readout in **Settings → Menu Bar**. Text, stacked, value, label and icon styles use the same live renderer as the other readouts. Celsius/Fahrenheit follows the existing global display setting. Unavailable conditions use a question-mark icon. The default summary shows the condition icon and temperature, humidity/cloud-cover percentage gauges, wind speed and a compass pointing toward the wind source (degrees clockwise from north), and sea-level pressure. It shows up to twelve actual upcoming model timestamps within 24 hours, with condition icons, relative lighter-accent temperature bars and full-accent precipitation-amount bars in mm over the explicitly labelled next 1/6/12-hour interval. The precipitation scale uses the largest valid shown amount. Periods may overlap and must not be summed or treated as hourly rates or probabilities. Known zero has no filled bar; missing or invalid amounts and unknown intervals have no bar. Tiny positives use a `<0.1` label and a one-physical-pixel minimum at native 1×/2×; inspection retains the numerical amount. Unknown intervals keep any valid amount but cannot set the scale. Columns are discrete model times, not a continuous time axis or interpolated hourly forecast. Point/click inspection exposes local date, time zone, value and interval. Daily tracks compare sampled low/high on one temperature scale; they are not guaranteed full-day extremes. Narrow System dropdowns show readable model-time rows (temperature and mm/period) and up to seven sampled daily ranges in a scrolling platter document; the window retains forecast columns and the sampled-range chart. **All readings** retains the next-48-hour temperature chart, all seven sampled daily ranges, the next 24 model timestamps, provider status and attribution. No fast-sampler Weather history is invented. Missing optional cloud cover/direction remain unavailable; stale/location-mismatched/paused/off forecasts are withheld. When no fresh forecast is available, the summary explains the reason without empty charts.

Choosing a city never changes the enable switch. **Locations & privacy…** edits custom coordinates without enabling Weather. Turning the main switch off cancels requests immediately, even if a location draft is invalid. No separate Weather setup entry appears in General settings.

## Local daylight estimates · 0.34.0

With Weather enabled and a valid selected location, **Estimated daylight** shows sunrise, sunset, duration and an accent daylight track beside the daily forecast. The track spans the actual civil day in the selected time zone, including 23/25-hour daylight-saving days and fractional offsets. Its dot marks the current minute. Inspect it for local date/time, UTC offset and whether that instant falls inside estimated daylight; **All readings** gives the same event times, duration and provenance. Polar states say **Sun up all day** or **Sun down all day** without inventing missing events. Very short intervals use a minimum visible width; times and duration are independently rounded to the nearest minute, so their displayed subtraction can occasionally differ by a minute. The window pairs the daylight track with daily ranges; the narrow dropdown stacks a numerical daylight platter below those ranges.

This is an independent local calculation using [NOAA/Meeus solar equations](https://gml.noaa.gov/grad/solcalc/calcdetails.html), a fixed −0.833° apparent horizon and Gregorian years 1901–2099. It adds no forecast request, permission, timer, dependency or saved history. A one-entry day/location cache is reused on existing updates. Terrain and actual atmospheric refraction are not observed; these are recreational estimates, with no global timing guarantee or navigation use claimed. Off, pause or missing/invalid coordinates removes the estimate. An authorized current-session/manual location can still supply daylight while the forecast is checking or stale; the local estimate and MET model have distinct provenance.

Reference comparisons, boundary regressions, native views and measured costs include independent USNO public-city checks and a live public Oslo forecast. Offscreen Light/Dark/polar images are synthetic renderer fixtures, separate from native-window checks. Moon information and daylight for configured world clocks remain future work.

## Provider, privacy and attribution

The supported provider is [MET Norway Locationforecast 2.0 compact](https://api.met.no/weatherapi/locationforecast/2.0/documentation). Requests go directly to `https://api.met.no/weatherapi/locationforecast/2.0/compact?lat=…&lon=…`. The provider receives the rounded coordinates and connection's IP address. Current-location mode uses TinyStats’ own macOS location permission. Manual/saved-city modes need no location permission. No IP geolocation, online location search, Weather account/token, API key or TinyStats server is involved. Names/time zones stay local and are not request parameters. New installs keep Weather off until an explicit opt-in; current-location forecasts also wait for an authorized current fix. Existing settings require their saved enablement choice. Isolated diagnostics/tests/benchmarks never enable Weather, read personal cities or request location implicitly.

Coordinates are rounded to three decimals, roughly 110 m in latitude; this is not an anonymity guarantee. The chosen coordinates/name/time zone are saved with local app preferences. Forecasts are retained only in memory. Disabling purges the forecast and shuts down its ephemeral session; a small bounded deadline ledger survives in memory to prevent opt-out/edit cycles from bypassing provider cache/rate limits. The next launch has no persisted forecast cache. App logs/diagnostics do not print weather coordinates or response bodies.

Data from MET Norway is licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) and NLOD 2.0; see its [licensing policy](https://api.met.no/doc/License). TinyStats converts temperatures and derives daily sample ranges. Attribution appears in Weather details, setup and embedded notices. Condition icons are native SF Symbols; provider icons/code are not copied. TinyStats is independent of MET Norway.

The [provider terms](https://api.met.no/doc/TermsOfService) require identification, cache-aware requests, rounded coordinates and traffic restraint. The client identifies TinyStats 0.37.4 and the project's GitHub repository URL (`https://github.com/letsopen-ai/tinystats`) in its User-Agent. A scaled deployment must reassess the provider's application-wide traffic limit and caching-proxy guidance before exceeding it; the desktop feature supplies no service-level guarantee.

## Scheduling and retained state

- The existing shared sampler schedules requests and checks a 30-second logical deadline. Weather uses a monotonic clock that includes sleep for cache age and rate limits; returned timestamps are projected into the sampler’s awake-time reference at each delivery. An effective receipt timestamp can be negative after long sleep; consumers compare elapsed differences, not a purported boot date. There is no weather timer, process scan, overlapping request or subprocess.
- Weather creates no forecast reader/session while disabled or waiting for current coordinates. Core Location is lazy, uses one outstanding fix, retries through shared sampler deliveries after five minutes on failure/30-second timeout, and normally refreshes after 30 minutes. It adds no timer. The enabled reader has one logical request and, while requesting, one serial delegate queue, with 20-second request/25-second resource timeouts. Pause/sleep cancel and invalidate active callbacks; manual/saved-city resume may reuse a still-fresh in-memory forecast. Current-location resume waits for a fresh fix. Each completed/cancelled URLSession is invalidated and released between requests, breaking its delegate retention cycle.
- Normal repeat requests wait at least 30 minutes plus 0–5 minutes of per-reader jitter, and no earlier than Expires or Cache-Control max-age/Age. A valid Last-Modified is reused as If-Modified-Since only with the matching cached forecast. HTTP 304 confirms that cache; it does not change the model's generation time. HTTP 203 is displayed as deprecated. HTTP 429/503 impose a global delay of at least one hour, honoring longer Retry-After values. Displayed waits beyond one year use “>1 year”; the underlying deadline is retained.
- Location changes have a one-minute global minimum. Up to eight unexpired coordinate deadlines are retained. If that inventory is full, a new location waits for a slot rather than evicting a deadline to request early. Such waits are visible in settings/details.
- The transport retains at most 256 KiB of decompressed body; framework-internal buffering is not claimed to share that cap. Decoding examines at most 512 ordered timestamps and retains up to 256 relevant points. Unknown/malformed units are withheld or fail the document; signed temperatures and real zero humidity/wind/precipitation remain valid.
- HTTPS/system certificate validation stays enabled. No cookies, stored account/proxy credentials, disk cache or result persistence is used. At most three redirects within the same HTTPS provider and forecast API family are accepted, preserving the coordinate query; cross-origin, downgraded and changed-coordinate redirects are rejected.

In 0.33.1, the summary still derives time-sensitive data on every shared tick, but skips accessibility/date formatting, redraw requests and hover reformatting when the derived presentation is unchanged. Minute, freshness, model-time, local-day, settings and unit changes remain live; existing locale/time notifications invalidate formatting. No new timer or forecast cache is added. See validation and scoped costs. The 0.33.2 Weather graphics evidence adds precipitation bars, semantic panel outlines in Light/Dark and clearer compact wind/pressure spacing without changing provider requests, collection or retained-state bounds. That release's populated images use a separate offline renderer fixture. The later 0.34.0 native public Oslo checks observe an exact-code populated forecast separately from synthetic fixtures. Provider payload arrival during resource sampling, broad live refresh/lifecycle coverage and resource acceptance remain open.

## Interpretation and rules

Locationforecast is a numerical model, not a weather station observation. **Now (forecast)** uses the most recent model timestamp at or before the current time, at most three hours old. The forecast must also have been checked within three hours and generated within the preceding 24 hours (allowing five minutes of clock skew). Stale data withholds the current menu value, chart and rule observations; details disclose its stale state.

Model intervals can change from hourly to wider periods. Upcoming rows use actual timestamps in the chosen time zone. Daily low/high is the range of available instant-temperature samples, not a guarantee of full-day extrema; the current day and sparse later days can be partial. A precipitation amount belongs to its actual next 1/6/12-hour interval, which is displayed explicitly. Missing data never becomes zero. See the [provider data model](https://api.met.no/doc/locationforecast/datamodel).

Rules support forecast temperature (always °C), wind (m/s) and next-hour precipitation (mm). A wider precipitation period cannot satisfy a next-hour rule. Weather opt-in and master notification opt-in are separate. Queued alerts recheck the current weather revision, enabled state, rule and monotonic freshness deadline; disabling/changing location/pausing prevents old queued delivery. Actual OS notification delivery remains a separate validation gate.

## Reproduction and limits

Ordinary tests and `--diagnose` make no weather request. The deterministic suite uses synthetic data and URLProtocol transport fixtures. An explicit live check uses a public provider example, never a personal location:

```sh
TINYSTATS_VALIDATE_WEATHER=1 swift test --build-system native --filter ownedOptInWeatherEndpointValidation
```

The benchmark’s separate `--weather` opt-in selects a public Oslo example (59.900, 10.700) in an owned preferences suite. `--weather-example met` instead uses the provider documentation example (60.000, 11.000). The suite is removed after its child exits:

```sh
python3 scripts/benchmark-app.py --preview --module weather --weather --weather-example met --warmup 30 --duration 60
```

Do not repeatedly relaunch live fixtures to bypass known response expiry. Long-run provider refresh/304 behavior, real proxy/VPN/sleep transitions, a broad location/model matrix and large-installation traffic remain unvalidated. Additional providers, place-name lookup, UV, moon information and severe-weather advisories remain future work; no accuracy calibration or official-alert service is claimed.

Clock contract: Apple distinguishes [awake system uptime](https://developer.apple.com/documentation/foundation/processinfo/systemuptime) from [monotonic clocks that include sleep](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time). Weather uses `clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)` internally, then projects its receipt/next-request times at the sampler’s provided uptime. A six-hour simulated sleep must age the cache, permit an expired refresh and leave the displayed next delay in minutes rather than hours of clock-origin difference. This is deterministic clock/lifecycle coverage, not a physical overnight-sleep test.
