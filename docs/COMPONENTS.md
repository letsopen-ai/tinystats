# CPU cores, GPU counters and sensor groups

GPU also shows **reported Metal GPU time by creating process**, in milliseconds per wall second, with bars relative to the leading row. Helpers and WindowServer remain separate. These are driver time counters, not device or physical-core utilization; completion bursts and overlap can exceed1000ms/s. Collection runs only for visible GPU details, within bounded existing accelerator traversal, with targeted process identities and no full process inventory. Missing/changing/reset/reused clients withhold their interval, zero remains valid, and known non-Metal presence preserves provenance. Close/switch/pause/reset clears baselines. M4/native evidence and schema/provenance limits; initial attachment cannot authenticate creator start at client birth, and other drivers/hardware remain unverified.

CPU’s graphical summary shows verified E/P secondary/primary-accent utilization rings in the window and capsules in dropdowns without visual core IDs; accessibility retains kind, identity and value. All readings exposes the available logical-core readings under Efficiency, Performance or neutral Logical headings. GPU metrics remain on the separate GPU page. Labels use explicit `logical-cpu-id` and `cluster-type` properties from the CPU device tree, matched to the Mach counter index. They are never inferred from the first/last half of a core list or a model's advertised counts. Duplicate IDs, invalid fields, unsupported types and missing records remain unknown. The bounded inventory refreshes at most once per minute, on count changes or after reset; rates continue using the existing shared sampler and reset rules.

The CPU per-core menu bar style uses a derived secondary system accent for verified efficiency cores and the primary accent for verified performance cores. Unclassified cores use a neutral label tint. Stored manual tint fields no longer override these colours. Accent and appearance changes redraw the graphics. Menu bar width remains bounded to the first 32 logical cores; CPU details expose the complete existing collector limit of 256. On Intel, logical cores can represent Hyper-Threading threads. TinyStats does not claim physical-core pairing or invent E/P classes for them. Temperature sensor suffixes are not mapped to logical CPU IDs without hardware evidence.

GPU details show driver-reported shader-core counts, device utilization, renderer utilization and tiler utilization separately, where available. These are different scopes: renderer/tiler percentages are engine counters, not numbered shader-core activity. TinyStats has no verified individual shader-core utilization adapter and marks that reading unavailable. It never divides device load by core count or repeats a device percentage in fabricated per-core bars. Model, registry identity and core count are cached at the existing 60-second GPU discovery cadence; only performance counters are polled at the shared cadence.

Sensor details group recognized readings by **CPU**, **GPU**, **Fans**, **Memory**, **Storage**, **Battery**, **Neural Engine** and **System**. Empty groups are omitted. CPU, GPU, memory and disk pages show matching readings; Power consolidates power/voltage/current and battery/accessory information. CPU/GPU cooling cards place the hottest recognized component temperature beside up to three readable fan speeds. Fan lists use explicit CPU/GPU naming when present; generic F0/F1 numbering is shared/unassigned, not proof of ownership. Those ambiguous fans can appear in both cooling views with that disclosure. **Unclassified** retains unknown keys and measured quantities instead of guessing their component. All readings retains raw keys and units; signed current and valid zero fan/power values remain intact. The menu sensor chooser follows the same group order.

Grouping is based on existing platform-aware temperature recognition, a small set of established SMC key conventions and the explicit IOReport model-power source. It is not a promise that every sensor exists, is calibrated, or has the same physical placement on every Mac. SMC reads remain read-only, with the existing 128-sensor limit and >=5-second cadence. Grouping adds no hardware collection, timer, network request or privilege. The Sensors browser adds the separate bounded recent-history buffer described below.

## Browse individual sensors

Sensors lives under **Advanced** in the sidebar, keeping ⌘7. It opens in **Summary** with hottest recognized CPU/GPU highlights, readable fans and selected named temperature/power readings. Catalog-named readings appear individually by component; multiple unnamed readings collapse into one nonselectable “N more …” row per group; a singleton is shown directly using its existing collector name. Ranges combine only the same kind/unit; mixed groups show counts by kind. **All readings / Summary** exposes every physical reading with its raw key, without saving the view choice. Counts exclude derived highlights. Physical fan and prominent power/battery readings appear once in their component group, including during search and All readings; Highlights contains only the distinct hottest-temperature projections. Their existing selection identities and initial-focus priority are preserved.

The first focus follows the menu bar sensor when available, then hottest CPU, hottest GPU, the first available highlight, and the first named selectable visible row in display order, falling back to any visible identity or the first matching physical reading when all are unnamed/collapsed. An existing selection lasts for this detail lifetime, including search and tab switches. Clicking or keyboard-selecting a reading shows its live value and recent graph. Browsing never changes the menu bar sensor.

Search matches friendly names, raw keys, component groups, native units and kinds in both views. A query reveals matching physical keys individually even in Summary; hottest highlights also match “hottest”, “max” and “cpu temp”/“gpu temp”. Search preserves the selected chart. Missing readings remain unavailable; temperatures without recognized CPU sensors show an unavailable CPU highlight with an All readings note, never a guessed temperature.

### Sensor groups and name policy

Specific catalog names earn individual Summary rows; a lone remaining unnamed reading also appears using its existing collector name. Group-prefix recognition (Apple Silicon `Te`/`Tp` CPU, `Tg` GPU and recognized M3 `Tf` groups) does not establish a physical location or per-key name. Unknown keys get no invented core numbering or cluster label. Intel logical-core conventions likewise retain their key in All readings unless a specific name is cataloged.

| Keys | Catalog name / scope | Provenance |

| TC0P, TC0D, TC0E, TC0F, TC0H, TCAD | CPU proximity, diode, virtual diode, filtered diode, heatsink, package | Established SMC conventions; VirtualSMC key reference below |
| TCGC, TB0T, Tm0P, TA0P | GPU temperature, Battery temperature, Memory proximity, Ambient | Established SMC conventions; VirtualSMC |

Recent browser history belongs to the current detail-view lifetime. It retains up to 120 actual sensor observations for each of 132 identities: the 128-SMC limit plus up to four model-power readings. The compact Float value payload is bounded to 63,360 bytes, plus dictionaries and a shared time axis. It reuses the existing ≥5-second hardware cadence, ignores cached repetitions, preserves missing/zero/signed values and units across disappearance, and restarts incompatible kind/time epochs. Hottest charts compute a read-only maximum over currently readable recognized temperature columns; samples with no contributing value remain gaps. No derived column is stored. Disappeared keys stop contributing, so these plots are not a historical maximum over every key ever seen. Time covered depends on the actual cadence. Closing releases the browser and buffer. This history is not the persisted selected-menu-sensor archive; the graph tooltip/AX help discloses its recent, view-local scope. See [History](HISTORY.md) and the iteration evidence.

## Sources and limits

Apple's [Mach host implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/host.c) returns load-info records in processor-array order. Apple's [CPU-count test](https://github.com/apple-oss-distributions/xnu/blob/main/tests/cpucount.c) uses the device tree's explicit logical IDs. Apple SDK IOKit/Mach headers supply the interfaces. The [VirtualSMC key reference](https://github.com/acidanthera/VirtualSMC/blob/master/Docs/SMCSensorKeys.txt) and already-attributed [Stats](https://github.com/exelban/stats) provide independent sensor protocol references. This implementation is original code; no proprietary code or assets are copied.

Read-only local M4 inspection observed ten explicit CPU IDs (six E and four P), GPU core count ten, and device/renderer/tiler GPU counters. Individual GPU-core activity, physical Intel sensors, other generations and calibration remain open work.

Sensor browser charts fit recorded values with numerical scale and unit-bearing hover/AX. Selected headlines retain the current value; redundant legends/statistics are omitted. Cached hardware timestamps leave existing rows alone; unchanged row presentation skips table reload. Resized tables reserve a trailing unit gutter. Reaching128 SMC readings displays a discovery-cap notice rather than implying exhaustive hardware discovery.

## CPU, Memory and Network process grouping

The shared native `ProcessGroupingControl` (`Processes | Apps`, small size) sits at the trailing end of the process-list section header, never above the dropdown cards. Summary headers reserve a fixed 122-point control gutter; All readings places the same control in the heading’s trailing table cell. It participates in native keyboard traversal and exposes “Process list grouping” to VoiceOver. Network previously had an AX label (“Network traffic grouping”), but no explicit AX identifier; the label now describes its shared scope. Existing footer and navigation identities remain unchanged.

One choice applies to all three modules. `Settings.processGrouping` reads/writes the original persisted `networkTrafficGrouping` key (`processes` / `bundles`), so old Network choices are preserved directly without a replacement key or conflicting preferences. Missing/invalid values still default to Processes; unrelated Settings drafts preserve the shared choice and Network revision. Mode changes while Network is selected rebaseline and reject stale deliveries. CPU/Memory toggles preserve the Network revision/snapshot and do not reset an inactive Network ledger. CPU/Memory changes rearm the existing shared schedule for a sample while their details are live, immediately if the last collection finished at least one second ago or at that one-second boundary otherwise; paused/asleep views keep the saved projection and never sample implicitly. No full ledger is retained for UI regrouping, and truncated process rows are never summed. Paused snapshots that already contain app projections retain them.

CPU Apps sums per-process CPU percentages (percent of one core); Memory Apps sums the existing physical-footprint metric. **Summing per-process footprint/RSS can double-count shared pages; it is not unique app RAM or a reconciliation with system used memory.** All readings and the Memory card’s hover/VoiceOver description disclose this caveat. Both projections aggregate the complete accessible general process scan (existing 8,192-row cap) before selecting the top eight groups; All readings retains its seven-row CPU/Memory presentation limit. Individual process mode and Disk I/O remain unchanged. CPU sums available, finite nonnegative member readings and ranks by that partial sum, counting unmeasured members in `cpuIncomplete` for a `≥` value prefix plus hover/AX disclosure. A group is nil if none of its members is measured; CPU/memory overflow stays unavailable. A newly spawned helper cannot blank or demote the measured app total.

`ExecutableBundle` is the shared, unit-tested lexical resolver used by CPU/Memory and Network: the outermost exact lowercase `.app/Contents/` component wins, including helpers under Contents/Frameworks and nested apps. Different paths stay separate; symlinks/case aliases are not normalized. Non-bundle, missing, exited or identity-changed paths remain individual PID rows; shared brokers are never guessed into a client app. Membership observes the executable now, not responsibility throughout a past interval. CPU/Memory counts include accessible scanned members; Network counts only owners with positive traffic in that complete interval.

App rows center text, 16-point icons and 22-point fills on the same row; fills start after the icon. Shared/unresolved rows use the same layout with a neutral placeholder and a separate count column. App icons have no artificial rim; the neutral semantic placeholder is one cached image. Counts use a 30-point gutter fitting four digits and 10-point label ink/tabular digits with process-count help (including one member); table cells reserve the same numeric count gutter and spell out the count in tooltip/AX. Tooltips/VoiceOver include counts and bundle paths. Display metadata/icons are fetched only for drawn/realized rows through a detail-lifetime, 32-entry main-actor FIFO cache. Worker collection never uses AppKit or filesystem metadata. See [Performance](PERFORMANCE.md#process-app-grouping-cost-and-bounds) for collection/cache bounds and cost estimates.
